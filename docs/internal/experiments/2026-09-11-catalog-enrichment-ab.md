# Does catalog enrichment actually improve routing? A single-variable A/B

**Date:** 2026-09-11 · **Model:** `claude-opus-5` · **Instrument:** `scripts/eval/route.workflow.mjs`
**Status:** answered. Recorded here rather than under `docs/internal/eval-results/` **on purpose** - see [Why this is not a scorecard](#why-this-is-not-a-scorecard).

## The question, and why the previous attempt could not answer it

The advisor's routing corpus (`skills/think-framework-advisor/references/recommendable.json`) carries three fields on every entry beyond name and description: `anti_triggers`, `not_use`, and `overlaps`. They are hand-authored, they cost maintenance, and nothing had ever tested whether they earn it.

The 2026-09-10 session produced a suggestive number and, correctly, refused to report it as a finding. Plain-roster routing scored right-alternative **114/128** against the enriched corpus's **122/128** - but *three* things differed between those two runs (router persona, corpus enrichment, and distractor count), so an 8-case gap belonged to no single cause. It went into the backlog as a question with the confound named.

This is the controlled version.

## Design

One variable. Everything else is held byte-identical between the two arms:

| held constant | value |
|---|---|
| instrument | `scripts/eval/route.workflow.mjs`, same commit |
| cases | the same 755 (376 trigger, 379 anti, 128 of the anti naming a specific alternative) |
| blind copy | the same `id` + `prompt` file, no answer key |
| router prompt | **identical**, and corpus-agnostic by construction (see below) |
| model | `claude-opus-5` |
| batching | 25 cases per agent, serial groups of 5 |
| day | both arms 2026-09-11, back to back |
| scorer | `scripts/eval/score.mjs`, same answer key |

| the one variable | arm A | arm B |
|---|---|---|
| corpus | `recommendable.json` as shipped | the same file with `anti_triggers`, `not_use`, `overlaps` removed |

**The control arm is provably a one-field delta.** It is generated by `scripts/eval/strip-corpus.mjs`, which refuses to write unless every retained field is byte-identical to the source, key order is preserved per entry, entry counts match, and at least one enrichment field was actually found to remove. Output: `63 skills + 9 recipes, key order preserved, 189 enrichment field(s) removed` (63 x 3).

**The prompt had to change first, and that is the subtle part.** `routePrompt` previously asserted that every catalog entry "has name, description, anti_triggers, not_use, overlaps". That is false of a stripped corpus, and a router told to expect absent fields will hunt for them or invent them - making the prompt a *second* variable in a single-variable experiment. It now says each entry has a name and description and that **some** also carry the other three, with an instruction to judge on whatever is present. That phrasing is true of both arms, so one prompt serves both.

**The control reproduced.** Arm A returned exactly the 2026-09-10 figures (376/376, 379/379, 122/128) on an independent run. That is what makes arm B's deltas attributable rather than noise.

## Result

| metric | A: enriched | B: stripped | delta |
|---|---|---|---|
| trigger top-1 | **376/376** (100%) | **376/376** (100%) | **0** |
| trigger top-3 | 376/376 (100%) | 376/376 (100%) | 0 |
| anti no-false-fire | **379/379** (100%) | **378/379** (99.7%) | **-1** |
| anti right-alternative | **122/128** (95.3%) | **113/128** (88.2%) | **-9** |
| unrouted | 0 | 0 | 0 |

Top-1 was **identical on 734 of 755 cases** (97.2%). Of the 21 that moved:

- **0 were trigger cases.** Every single one was an anti case.
- 13 the enrichment got right and the stripped corpus got wrong.
- 5 the stripped corpus got right and the enrichment got wrong.
- 3 both got wrong, differently.

## What it means

**The enrichment fields do nothing for trigger accuracy and everything for anti-case behaviour.** 376/376 in both arms; all 21 changes were anti cases. That is not a curiosity, it is the result being mechanically coherent with what the fields *are*: `anti_triggers` and `not_use` describe when **not** to reach for a framework, so they can only move behaviour on situations where the answer is "not this one". An experiment whose effect showed up somewhere else would have been evidence that it measured the wrong thing.

**They prevent a false fire.** Stripping them introduced one, on the same prompt that is the single false fire in the skill-selection eval: *"I have twenty candidates to rank by forced pairwise comparison."* With `not_use` present the router answered `none`; without it, it grabbed `pairwise-comparison`. Twenty candidates is 190 pairs, which is exactly what that field exists to say.

**They make the router more decisive, and that cuts both ways.** This is the honest reading rather than "enrichment is better":

- On anti cases that name a correct alternative, decisiveness helps (+13). Without `overlaps` and `not_use`, the router fell back to `none` on cases where a *different* shipped skill was the right answer - four `parallel-perspectives-review` stakeholder cases, two `decision-option-review` cases, one `brainwriting`, one `theory-of-constraints`, and it confused `red-team-light` with `premortem` twice.
- On anti cases where the right answer genuinely is "no tool", decisiveness hurts (-5). All five cases the stripping improved are `expected: none` cases where the enriched router over-reached: *"Brainstorm 20 feature ideas and group them by theme"*, *"Forecast next year's revenue with a range"*, and three more of that shape.

Net on the changed cases: **+8 for the enrichment**, and the aggregate right-alternative gap of 9 agrees. So the fields earn their maintenance cost - but they buy *discrimination between neighbours*, not restraint, and they make a small number of no-tool prompts slightly harder to decline. If the over-reach on `expected: none` cases ever matters more than the neighbour discrimination, the lever is `not_use` coverage on the over-reaching skills, not removing the enrichment.

**The 2026-09-10 suggestion was directionally right.** It guessed an 8-case gap on right-alternative with three confounds; the controlled experiment finds 9 with one variable. Recording the earlier number as a question rather than a finding was the correct call, and the answer happens to vindicate the guess without having depended on it.

## Limits

- **One run per arm.** Model-executed and non-deterministic; the deltas here are small integers and a repeat would move them. The 0-difference on 376 trigger cases is the robust part; the -9 on 128 right-alternative cases is one observation.
- **The 5 counter-cases are not noise to be dismissed.** They are a consistent pattern (enrichment over-reaches on `expected: none`), and they would need their own run to size properly.
- **This tests the corpus, not the advisor.** It measures whether a blind router discriminates better with the fields present. It does not measure whether the live advisor's Thinking Plans are better, which is the output eval's question.
- **Both arms are the same model.** Nothing here says the fields help a smaller or different model equally; they might matter more.

## Why this is not a scorecard

Deliberately filed under `docs/internal/experiments/`, not `docs/internal/eval-results/`, and neither arm went through `finalize.mjs`:

1. **Arm B routed against a corpus that does not ship.** Finalizing it would stamp 63 `skill.meta.yml` sidecars with a measurement taken against a catalog no user has. `route.workflow.mjs` and `strip-corpus.mjs` both say so in their headers.
2. **Gate layer 15 would demand a paired `.json` and a totals contract** for anything in `eval-results/`, which is the right rule for a published trust number and the wrong shape for an experiment with two arms and no single headline.

Arm A's figures are legitimate and *do* match the committed 2026-09-10 scorecard; they are reported here as the experiment's control, not as a replacement for it.

## Reproducing it

```bash
node scripts/eval/extract-cases.mjs > ab-cases.json          # 755 cases, the answer key
#   write a blind copy: [{id, prompt}] only
node scripts/eval/strip-corpus.mjs recommendable-stripped.json

#   arm A - the shipped corpus
#   Workflow scriptPath: scripts/eval/route.workflow.mjs
#            args: {blindPath, count: 755, batchSize: 25,
#                   corpusPath: "skills/think-framework-advisor/references/recommendable.json"}
#   arm B - identical, with corpusPath pointing at recommendable-stripped.json

node scripts/eval/score.mjs ab-cases.json ab-routed-enriched.json
node scripts/eval/score.mjs ab-cases.json ab-routed-stripped.json
```

Each arm: 31 blind router agents, 0 errors, 0 unrouted. Roughly 3.7M and 3.1M subagent tokens respectively.

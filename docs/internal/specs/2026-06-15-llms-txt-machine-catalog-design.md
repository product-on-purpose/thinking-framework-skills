# Design spec: generated `llms.txt` + machine-readable catalog

- Date: 2026-06-15
- Status: approved (brainstorming), pending implementation plan
- Branch: `feat/llms-txt-catalog`
- Author: maintainer + Claude (opus 4.8)
- Tracking: post-v0.8.0 "what's next" item #2 (acquisition-side, data-independent)

## 1. Context and motivation

v0.8.0 shipped the learn-by-example layer and a measurement loop. The next
strategic call (conversion vs. acquisition) is gated on GA4 data, which is not
yet flowing. The recommended data-independent move is acquisition-side: make the
library discoverable and routable by *other* agents and crawlers.

The `llms.txt` convention (llmstxt.org) is a site-root markdown index that an LLM
or agent can fetch to understand what a site offers and where to go. Paired with
a machine-readable JSON catalog, it lets an external agent discover every
thinking skill, learn what each does and when to use it, and route to or chain
the right one. This is cheap, deterministic, on-brand (agent-executable skills
for agents), and needs no analytics.

The whole artifact set is GENERATED from existing sources of truth and
drift-gated in CI, so it carries no hand-maintenance cost and cannot silently go
stale.

## 2. Goals and non-goals

### Goals

- A single generator, `scripts/gen-catalog.mjs`, that emits three artifacts from
  the existing sources of truth, with a `--check` drift mode wired into the
  conformance gate.
- `llms.txt`: the llmstxt.org convention index for the invokable surface plus key
  docs, served at the site base.
- `catalog.json`: a rich, routing-and-chaining-focused list of the 69 invokable
  components (56 framework skills + 4 tools + 9 recipes).
- `evaluated.json`: the complete 135-method registry projection, so the 79
  evaluated-but-not-shipped methods are captured in full context (the "other
  document" requested during brainstorming).

### Non-goals (out of scope for this work)

- `llms-full.txt` (the full-content inlined variant). Possible later; not now.
- Any GA4 / analytics dependency.
- Changing the registry, skills, recipes, or site routes. This work only reads
  them and emits new passthrough files.
- A version bump. This is additive generated infra; it rides the next release
  with a CHANGELOG `[Unreleased]` entry, matching how PR #64 (the example-coverage
  ratchet + measurement loop) was handled.

## 3. Artifacts and locations

All three files are generated into `site/public/`, which Astro copies verbatim to
the built site root. With the published base `/thinking-framework-skills`, they
are served at:

| File | Served at | Covers |
|---|---|---|
| `site/public/llms.txt` | `<base>/llms.txt` | invokable surface, grouped, + key docs |
| `site/public/catalog.json` | `<base>/catalog.json` | 69 invokable entries (rich) |
| `site/public/evaluated.json` | `<base>/evaluated.json` | all 135 registry methods (lean) |

Note (accepted limitation): GitHub Pages serves a project site under a subpath,
so these are at `<base>/llms.txt`, not the true domain root `/llms.txt`. The true
domain root belongs to the org's other content and is not ours to write. This is
the same constraint the existing `public/robots.txt` lives under.

## 4. Data sources and the join

The generator is zero-dependency Node (like every script in this repo) and reads
UTF-8 explicitly (Windows cp1252 would otherwise corrupt output). Sources of
truth, by component type:

| Component type | Count | Roster source | Per-entry detail |
|---|---|---|---|
| framework skill | 56 | `frameworks/registry.mjs` (status `shipped`) | `SKILL.md` frontmatter + `skill.meta.yml` |
| tool (meta-skill) | 4 | `library.json` (the 4 meta-skills) | `SKILL.md` frontmatter + `skill.meta.yml` |
| recipe | 9 | `_workflows/*.md` | recipe frontmatter (`steps`) |
| evaluated method | 135 | `frameworks/registry.mjs` (all) | registry fields only |

The 4 tools are `think-framework-advisor`, `think-research-framework`,
`think-top3`, `think-random-frameworks` (the meta-skills set already named in
`gen-recommendable.mjs`). They are skills in `library.json` but are not framework
methods, so they are not in the registry; their detail comes from their own
`SKILL.md` / `skill.meta.yml`.

This mirrors the existing `gen-recommendable.mjs` join (library.json + SKILL.md +
_workflows), extended with the registry (for framework mechanism/tier/aliases)
and `skill.meta.yml` (for artifact type and companions).

## 5. `catalog.json` schema (the invokable surface, rich)

Top-level envelope (matches `gen-recommendable.mjs` style):

```jsonc
{
  "$note": "GENERATED by scripts/gen-catalog.mjs - do not hand-edit. ...",
  "generated_from": "frameworks/registry.mjs + library.json + skills/*/SKILL.md + skills/*/skill.meta.yml + _workflows/*.md",
  "site": "https://product-on-purpose.github.io/thinking-framework-skills/",
  "counts": { "skills": 56, "tools": 4, "recipes": 9, "total": 69 },
  "entries": [ /* sorted: skills, then tools, then recipes; each group A->Z by slug */ ]
}
```

Per-entry shape, by `type`:

### `type: "skill"` (framework) and `type: "tool"`

```jsonc
{
  "slug": "premortem",
  "type": "skill",
  "invocation": "think-premortem",            // installable name an agent calls
  "name": "Premortem",                         // display name
  "family": "risk-and-resilience",             // skill metadata.family
  "evidence_tier": "S/M",                       // registry tier (skill); from SKILL.md for tools; null if n/a
  "mechanism": "stress-test a plan by imagining it already failed ...",  // registry oneLine (skill); SKILL.md summary for tools
  "when_to_use": "Use when about to commit to a launch, hire, ...",      // SKILL.md description, full
  "artifact": "risk-register",                  // skill.meta.yml interface.primary_artifact_type
  "status": "active",                           // library.json status
  "aliases": ["prospective hindsight"],         // registry aliases (skill); [] for tools
  "in_recipes": ["stress-test-decision"],       // recipes whose steps include this skill (reverse-derived)
  "likely_companions": ["think-decision-option-review", "think-what-would-have-to-be-true"],
  "url": "https://product-on-purpose.github.io/thinking-framework-skills/frameworks/think-premortem/"
}
```

### `type: "recipe"`

```jsonc
{
  "slug": "stress-test-decision",
  "type": "recipe",
  "invocation": "think-stress-test-decision",
  "name": "Stress-test a decision",
  "when_to_use": "...",                         // recipe frontmatter description
  "steps": ["think-decision-option-review", "think-premortem", "..."],  // ordered skills it runs
  "url": "https://product-on-purpose.github.io/thinking-framework-skills/recipes/stress-test-decision/"
}
```

### Field provenance and edge rules

- `evidence_tier` for framework skills comes from the registry (single source of
  truth for tier, already gate-checked against SKILL.md). For tools it comes from
  `SKILL.md metadata.evidence-tier` or is `null` if a tool has none.
- `mechanism` for framework skills is the registry `oneLine`. Tools have no
  registry entry, so their `mechanism` is the first sentence of the `SKILL.md`
  body summary (or the description) - clearly the same role (a one-line "what it
  does").
- `artifact` is `skill.meta.yml interface.primary_artifact_type`. All 60 skill
  dirs carry this field (verified), so it is reliably present for every skill and
  tool. Recipes omit `artifact` and carry `steps` instead.
- `in_recipes` is reverse-derived: read every `_workflows/*.md` `steps` list,
  invert to a skill-slug -> [recipe-slug] map. A skill in no recipe gets `[]`.
- `likely_companions` is from `skill.meta.yml` (`execution.likely_companions`,
  falling back to `relationships.complements`). The meta.yml stores these as ids
  (`thinking-framework-skills.<slug>`); the generator maps each id to its
  invocation name (`think-<slug>`) so the catalog is self-referential by the same
  key it uses everywhere else (`invocation`). An id that does not resolve to a
  shipped skill is dropped (and a warning printed), so the field never names a
  non-existent skill.
- `url` is built from `package.json homepage` + the route pattern for the type:
  skills -> `frameworks/<invocation>/`, tools -> `tools/<invocation>/`, recipes ->
  `recipes/<slug>/`. Every emitted `url` path is checked against
  `scripts/route-manifest.txt` (the live-route source of truth) at generate time;
  a path with no matching route fails the generator loudly rather than emitting a
  dead link.

## 6. `evaluated.json` schema (the complete 135 registry projection)

Leaner, because most entries are non-invokable. This is the honest, complete
"everything we graded and why" reference; the 79 not-shipped methods are simply
the `status != "shipped"` subset.

```jsonc
{
  "$note": "GENERATED by scripts/gen-catalog.mjs - do not hand-edit. ...",
  "generated_from": "frameworks/registry.mjs",
  "counts": { "total": 135, "shipped": 56, "not_shipped": 79 },
  "families": [ { "slug": "...", "name": "..." } ],   // the 13 catalog families
  "methods": [
    {
      "slug": "six-thinking-hats",
      "name": "Six Thinking Hats",
      "family": "perspective-shifting-and-multi-lens",
      "tier": "X",
      "status": "flag",                 // shipped | fold | reject | flag | ...
      "verdict": "reject",
      "fold_into": null,                // where a folded method actually ships, else null
      "mechanism": "branded parallel-thinking ritual",   // registry oneLine
      "url": "https://.../library/six-thinking-hats/"     // /library/<slug>/ dossier if one exists, else null
    }
  ]
}
```

- `fold_into` surfaces the registry `foldInto` so an agent learns where a folded
  method's capability actually lives (e.g. steelmanning -> red-team-light).
- `url` is the `/library/<slug>/` Framework Library dossier when the entry has one
  (most documented entries do, after the v0.7.1 depth pass). When no dossier page
  exists, `url` is `null`. As in section 5, any non-null path is validated against
  `route-manifest.txt`.

## 7. `llms.txt` structure (llmstxt.org convention)

Markdown, absolute URLs (the file is fetched out of page context, so relative
links would not resolve). Shape:

```
# Thinking Framework Skills

> One-paragraph summary: an evidence-graded library of agent-executable
> thinking-method skills for Claude Code, Codex, and other AI agents. <count>
> skills across <n> families, each producing a concrete artifact.

Machine-readable: [catalog.json](<base>/catalog.json) (invokable skills, tools,
recipes) and [evaluated.json](<base>/evaluated.json) (all 135 evaluated methods).

## Start here
- [Getting started](...): install and first run
- [Showcase](...): worked, end-to-end examples
- [Does this work?](...): the behavioral-eval results
- [Using the frameworks](...): the operating guide

## Skills
### <Family display name>
- [think-<slug>](<url>): <one-line mechanism>
...one subsection per family that has shipped skills...

## Tools
- [think-framework-advisor](<url>): <one-liner>
...

## Recipes
- [think-<slug>](<url>): <one-liner> (steps: a -> b -> c)
...

## Evaluated, not shipped
We graded 135 methods; <n> ship as skills. The rest are documented with the
reasoning in the Framework Library. See [evaluated.json](<base>/evaluated.json)
and the [Framework Library](<base>/library/).
```

All counts and links are generated, so they never drift from the registry.

## 8. Generator design (`scripts/gen-catalog.mjs`)

- Zero dependencies; explicit UTF-8 read/write. Structured like
  `gen-recommendable.mjs`.
- Default run writes the three files into `site/public/` and prints a summary.
- `--check` mode regenerates in memory and compares against the committed files;
  exits non-zero listing any stale file (so CI fails with an actionable message).
  It guards all three files, exactly as `gen-recommendable --check` guards both
  its outputs.
- npm script: `"gen:catalog": "node scripts/gen-catalog.mjs"`.
- Small shared helpers (frontmatter reader, recipe-step parser) already exist in
  `gen-recommendable.mjs` / `scripts/lib/`; reuse rather than duplicate where
  practical.

## 9. Gate integration

`scripts/check.mjs` gains an 8th layer: `gen-catalog.mjs --check`. Placed after
the example-coverage ratchet, run unconditionally (so all problems surface at
once), and folded into the final exit-status OR. The header comment in
`check.mjs` is updated from "seven layers" to "eight layers" with the new layer
described.

No new CI workflow is needed: `check.mjs` already runs in CI. The route-parity
and rendered-links guards are untouched because:

- `llms.txt`, `catalog.json`, `evaluated.json` are `public/` passthrough files,
  not Astro routes, so `check-route-parity.mjs` (which compares Astro routes to
  the manifest) does not see them and `route-manifest.txt` does not list them.
- `check-rendered-links.mjs` scans built `.html`; it ignores `.txt` and `.json`.

This is verified by how `public/robots.txt` and `public/favicon.svg` already
coexist with both guards.

## 10. Verification plan

- `node scripts/gen-catalog.mjs` writes 3 files; manual inspection of a few
  entries against their `SKILL.md` / `skill.meta.yml` / registry source.
- `node scripts/gen-catalog.mjs --check` is clean immediately after a generate,
  and (negative test) reports stale after a deliberate hand-edit to one output.
- `node scripts/check.mjs` passes with the new 8th layer (rc=0).
- `npm test` still 43/43.
- `npm --prefix site run build` succeeds and the three files appear in
  `site/dist/` at the root (passthrough confirmed).
- `node scripts/check-rendered-links.mjs site/dist` and
  `node scripts/check-route-parity.mjs site/dist` still pass (guards unaffected).
- Spot-check that every `url` in both JSON files resolves to a path present in
  `site/dist` (the generator's route-manifest check should make this hold by
  construction).
- A JSON parse of both files (valid JSON) and a quick assertion of counts
  (catalog 69, evaluated 135).

## 11. Edge cases and decisions

- A new shipped skill automatically appears in `catalog.json` and `llms.txt` on
  the next generate; if a contributor forgets to regenerate, layer 8 reds CI. This
  reinforces (does not conflict with) the example-coverage ratchet.
- A folded/rejected method appears only in `evaluated.json`, never in
  `catalog.json` (it is not invokable).
- Tools have no registry entry and (some) no evidence tier; the schema allows
  `null` and the generator degrades gracefully rather than inventing values.
- The 13th family (ethics-values-deliberation) and any future family flow through
  automatically because families are read from the registry, not hardcoded.

## 12. Future (explicitly deferred)

- `llms-full.txt` (inlined full content) once there is demand.
- Linking `llms.txt` from `robots.txt` / site `<head>` for discoverability.
- A generated JSON Schema published alongside `catalog.json` for consumers.

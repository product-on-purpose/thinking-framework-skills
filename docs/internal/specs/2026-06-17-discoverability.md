# Spec: discoverability pass (activate the agent-discovery surface)

**Status:** proposed (not started).
**Owner:** maintainer-gated build.
**One line:** v0.9.0 built a machine-readable catalog for AI agents and crawlers (`llms.txt`, `catalog.json`, `evaluated.json`) but linked it from nowhere. This pass puts up the signs so the surface is actually found, and adds the one expanded file the convention expects.

## Problem

The site serves three machine-readable files at the root, generated by `scripts/gen-catalog.mjs` into `site/public/` and copied verbatim by Astro:

- `llms.txt` - the [llmstxt.org](https://llmstxt.org) index (what the site is, the invokable surface, key docs).
- `catalog.json` - the 69 invokable components (56 skills + 4 tools + 9 recipes) with routing metadata.
- `evaluated.json` - all 135 evaluated registry methods.

Nothing points to them. `robots.txt` advertises only the sitemap; no page `<head>` references `llms.txt`; there is no `llms-full.txt`. An AI assistant or crawler that lands on the site cannot discover the index without guessing the URL. The strategic bet of v0.9.0 ("be discoverable by agents") is built but switched off.

## Goals

1. Make `llms.txt` discoverable from the two places agents and crawlers look: `robots.txt` and the page `<head>`.
2. Add `llms-full.txt` (the expanded variant the convention pairs with `llms.txt`), generated by the same pipeline and held by the same drift gate.
3. Keep everything inside the existing generate-and-gate machinery, so the discovery surface cannot silently drift.

## Non-goals

- **Distribution.** Posting, outreach, submitting to directories, marketplace promotion: those drive traffic and are the maintainer's to do. This spec only removes the technical reasons the surface is not found. The companion **launch writeup** (below) is the one distribution *asset* this work produces; shipping it is still a human action.
- **Per-page `og:image` / social cards.** Deliberately omitted today and owned by the shared `astro-docs-preset` (clause 14.9; see `[[project_tfs-astro-site-standard]]`). Adding a per-repo `og:image` would deviate from the family standard, so it is out of scope here and tracked as a separate standard-level decision.
- **structured-data / JSON-LD** is documented as an optional follow-on (section 5), not part of the core build.

## Design

### 1. robots.txt - advertise the index

`site/public/robots.txt` today:

```
User-agent: *
Allow: /

Sitemap: https://thinking-framework-skills.productonpurpose.com/sitemap-index.xml
```

Add an `llms.txt` pointer (a comment is the de-facto convention; there is no ratified robots directive for it) and keep the machine files explicitly crawlable:

```
User-agent: *
Allow: /

# Machine-readable index for AI agents (llmstxt.org):
# llms.txt:      https://thinking-framework-skills.productonpurpose.com/llms.txt
# llms-full.txt: https://thinking-framework-skills.productonpurpose.com/llms-full.txt
Sitemap: https://thinking-framework-skills.productonpurpose.com/sitemap-index.xml
```

The origin is the same absolute one `gen-catalog.mjs` uses (`package.json` `homepage`); keep it literal here (robots.txt is a sanctioned base-literal exception alongside the sitemap line).

### 2. Site `<head>` - link the index from every page

In `site/astro.config.mjs`, the Starlight `head` is currently `gaHead` (the conditional GA tags, lines 19-27, 74). Add a persistent `<link>` that advertises `llms.txt` on every page, served alongside GA:

```js
// a persistent head tag, always present (unlike the GA tags, which are env-gated)
const discoveryHead = [
  { tag: 'link', attrs: { rel: 'alternate', type: 'text/plain', href: `${BASE}/llms.txt`, title: 'llms.txt' } },
];
// ...
head: [...discoveryHead, ...gaHead],
```

Notes:
- `BASE` is the single source (`scripts/site-base.mjs`); it is `''` for this root-served domain, so `href` resolves to `/llms.txt`. Do not hardcode `/`.
- `rel="alternate" type="text/plain"` is the pragmatic advertisement (there is no ratified `rel` for `llms.txt` yet); `title="llms.txt"` names it. This is the in-`<head>` signal crawlers and agents read.

### 3. llms-full.txt - the expanded variant

`llms.txt` is an index of links; the convention pairs it with `llms-full.txt`, which inlines the content so an agent ingests the catalog in one fetch instead of crawling ~200 pages.

In `scripts/gen-catalog.mjs`:
- Add `renderLlmsFullTxt(catalog, evaluated)` next to the existing `renderLlmsTxt` (line ~241). It emits the same header, then, for every invokable component in `catalog.json`, an inlined block: name, invocation, family, evidence tier, mechanism/when-to-use, the artifact it produces, and its URL. Append the evaluated-but-not-shipped summary the same way `llms.txt` does.
- Add `['llms-full.txt', llmsFull]` to the `FILES` array (lines 291-293). Because the gate (`gen-catalog.mjs --check`, `check.mjs` layer 8) byte-compares every entry in `FILES`, `llms-full.txt` is drift-checked automatically: no extra gate wiring.
- Add the `gen:catalog` regen to the change (it already runs on any roster change).

Reference `llms-full.txt` from `llms.txt`'s machine-readable line (next to the `catalog.json` / `evaluated.json` links) and from `robots.txt` (section 1).

### 4. Verify the surface is live

After deploy, the three existing files plus `llms-full.txt` serve HTTP 200 at the root; `robots.txt` shows the pointers; view-source on any page shows the `<link ... href="/llms.txt">`.

### 5. Optional follow-on (documented, not in this build): structured data

Add schema.org JSON-LD to the generated framework pages (`gen-site.mjs`) - e.g. `TechArticle` / `HowTo` / `SoftwareSourceCode` per skill - so search engines and AI assistants can parse what each page is and are eligible to surface it as a rich result. Heavier (touches the page generator and needs per-type modelling); spec it separately if section 1-3 shows the discovery channel is worth deepening.

## The companion launch writeup (separate deliverable)

A single long-form post whose hook is the honesty/measurement angle, drafted from the real eval numbers:

> Most thinking-tool libraries ask you to take their value on faith. We measured ours: 99% routing accuracy, zero false-fires across 673 cases, 99% of 315+ output checks. Here is how, and what it does and does not prove.

- Draft to `_local/marketing/` (gitignored), reusing `start/does-this-work` and the evidence model.
- It is a distribution *asset*; posting it (blog, Show HN, the existing LinkedIn drafts) is the maintainer's action. Build-and-hand-off, not build-and-ship.

## Tasks (ordered, agentically executable)

1. Edit `site/public/robots.txt` (section 1).
2. Edit `site/astro.config.mjs`: add `discoveryHead`, set `head: [...discoveryHead, ...gaHead]` (section 2).
3. Edit `scripts/gen-catalog.mjs`: add `renderLlmsFullTxt`, wire into `FILES`, cross-link from `llms.txt` (section 3); run `node scripts/gen-catalog.mjs` to emit `llms-full.txt` and refresh the others.
4. Run the gate + build + guards + tests; commit the four `site/public/` artifacts plus the two source edits.
5. (Separate) draft the launch writeup to `_local/marketing/`.
6. PR, gate-green, merge, deploy; verify the four files + the `<head>` link live.

## Out of scope / explicitly the maintainer's

Real acquisition: announcing, posting the writeup, submitting the site to AI/agent and plugin directories, backlinks, marketplace promotion. This spec makes the site *findable and parseable*; turning that into traffic is distribution work.
